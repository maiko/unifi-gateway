# UXG Pro qualification record

These results apply to the historical UXG Pro profile. The [coverage tracker](coverage.md) records the current Enterprise acceptance criteria and build-specific verification.

## Scope

UniFi owns desired state for explicitly mapped interfaces and features. VyOS owns actual state and operator-managed configuration. Reach VyOS through its supported management interface with TLS verification, a dedicated secret, and a management path independent of the routed test networks.

A verified workflow starts in the native Network UI, changes actual router behavior, and reports the resulting state accurately. Each combination of enabled features needs the same checks against the affected and unrelated traffic.

## Controller and topology

The controller ran UniFi OS Server 6.0.21 RC with Network 11.0.104-37279-1. The router ran stock VyOS 2026.11.22-0018-rolling. Two client VLANs (110 and 120) and two simulated WANs (210 and 220) used independent links. VyOS HTTPS API reads used certificate verification on the dedicated management path.

No physical UXG Pro was available. The site initialized zone-based policy and built-in zones. The candidate identified as UXG Pro, negotiated AES-GCM, and received its first `setparam`. The controller generated actual ordered `LAN_LAN` policy after the device advertised the observed filter and mangle schema versions. The sanitized baseline and native create, edit, and delete snapshots are in `tests/fixtures/uxg_pro/zbf-native-snapshots.json`.

## Inspection

Native Network buttons generated UDAPI inspection schema 8. **Notify** sent `pcap-high`, **Notify and Block** sent `pcap-l3-blocking-high`, and **Off** sent an explicit disabled object. The active VLANs were identified as `br110` and `br120`. Device provisioning supplied message broker schema 3 and per-device mutual TLS and AMQP credentials. The controller stored two observed Suricata events as **Threat Detected** and **Threat Detected and Blocked** and displayed both flows. The confirmed route is UTF-8 `text/plain` containing a JSON `SuricataEvent`, published into the local `unifi_flow_queue`. The first `application/json` attempt failed Java message conversion. This was a scoped publisher proof. The UI did not drive the engine or event transport automatically.

Sanitized native mode excerpts and their parser cover the three UI modes, duplicate keys, unmapped bridges and unsupported settings. EVE tests cover alert, drop, unknown verdict, IPv6 normalization, and a repeat after process restart. The lab used an independently written harmless marker on Suricata 7.0.10. The publisher records broker-confirmed delivery in a private SQLite journal and holds uncertain outcomes for verification. A production signature feed remains open.

A late-priority NFQUEUE hook passed live VyOS qualification without editing the router configuration. Its exact rules read back from the kernel, both directional counters advanced, and engine loss followed the chosen bypass. Running and saved VyOS configuration and the existing firewall matched the preflight snapshots.

UniFi OS Server 6.0.21 RC and Network 11.0.104-37279-1 drove the real VyOS 2026.11.22-0018-rolling actuator. Native **Notify** passed the marker from VLAN 110 and the receiver on VLAN 120 logged all 27 request bytes. The same source port appeared as an allowed Suricata alert. Native **Notify and Block** passed the benign control, and the marked request reached the receiver with zero application bytes and no reply. EVE confirmed a final drop for that source port. Both events appeared in the native System Log after correlating actual same-engine EVE flow counters and publishing through the pinned broker. A publisher restart and replay emitted no duplicate. Stopping the verified engine led to bypass, and UniFi logged **Gateway Configuration Failed**. The controller resent the revision and the daemon verified recovery. Native **Off** subsequently restored the marked request and made the owned engine and hook absent. The actuator constrained inspection to the approved IPv4 TCP lab flow on port 18743. A short comparison measured 649, 579 and 443 Mbit/s goodput and 1.035, 1.073 and 1.250 ms median transaction latency in Off, Notify and Block respectively. Kernel and netlink queue drops stayed zero in the inline test. Automated event collection, IPv6 and behavior with flow offload enabled still need qualification.

## WAN failover

WAN failover research used `services/wanFailover` version 11 and capability `0x4` while router writes were suspended. The native single-WAN, dual-WAN Auto, dual-WAN pinned ICMP SLA, and reversed priority snapshots are preserved as sanitized fixtures. The native user action changed WAN1/WAN2 metrics independently of the two SLA definitions. Its companion actions include two table-specific defaults, WAN NAT, and generated firewall and bridge changes. The lab removed the test WAN and both SLAs, verified the restored snapshot exactly matched the starting captured snapshot, and resumed the normal daemon.

A separate stock `protocols failover` test installed `198.19.210.242/32` via WAN 210 and WAN 220 at metrics 10 and 20. LAN 120 TCP and an exact forwarded FIB lookup proved primary, failover with both carriers UP, withdrawal with both target replies suppressed, and recovery to the first path. The test restored both peers' ICMP settings and removed the route, daemon, peers, addresses, and sockets. The stock daemon can flush protocol 111 in every table and uses binary ICMP checks with its own timing. [Stock failover implementation](https://github.com/vyos/vyos-1x/blob/f1789c0dbf7d0f3e5254caf6f750a5b670a2ca98/src/helpers/vyos-failover.py)

The live native **Failover Only** gate passed for the same two isolated WANs and both LANs. Network compiled the same policy in either WAN array order, so decoding keys on interface identity and metric while checking that all companion sections use the observed order. The integrated transaction verified and saved the two IPv4 defaults and four scoped masquerades. Native create sent fresh TCP from both LANs to WAN 210, with the peer seeing `198.18.210.1`. Removing only its ICMP replies shifted both flows to WAN 220 and source `198.18.220.1` while carrier stayed up. The observed native uplink changed to `eth2` and returned to `eth0` on probe recovery. The native metric edit then made WAN 220 primary with both peers healthy. During a second controlled loss, Network showed WAN 220 Offline, WAN 210 Online, and `eth0` active. Both had shown Online while their routes were available. The durations are time observed in the route state, with no synthetic latency or percentage. Auto SLA was rejected without changing the last verified routes. Network initially refused to remove WAN2 while the last verified active uplink was WAN2. It accepted removal after an acknowledged native change made WAN1 active. Returning WAN1 to Auto and removing both test SLAs restored the starting site. The withdrawal was acknowledged, the VyOS failover root and four NAT rules were absent, and numeric protocol 111 and the default FIB were empty. The peers, listeners and probe addresses were removed and both ICMP settings restored. The tested step leaves exact native SLA timing, IPv6, weighted load balancing, continuous Internet history, and concurrent VPN, OSPF or unrelated NAT open.

## QoS

Native QoS **Limit** wire capture used the same single-WAN lab after that restoration. The controller emitted a `v4only` `FW_QOS` classifier on `eth0` for VLAN 110 traffic to `198.18.210.2`. The classifier's queue name links to the rates in `udapi.qos.fw.queues`. Controller capability `udapi_caps & 0x100` was sufficient with filter 4, mangle 6 and sets 1, without a separate QoS version entry. The native change from 3 to 5 Mbps upload changed the corresponding integer from 3000 to 5000 Kbps and kept download at 8000 Kbps. Removal withdrew both the classifier and queue. The create, edit and withdrawal projections are in `tests/fixtures/uxg_pro/native-qos-speed-limit-snapshots.json`. Router writes were suspended for this capture.

Network 11.0.104 and stock VyOS 2026.11.22-0018-rolling passed the native lifecycle. The bridge installed two stock HTB egress shapers and two exact IPv4 forward markers with `continue` verdicts. The kernel check verifies the mark selectors, HTB rates, and default queues on the other interfaces before acknowledging a change. VyOS resets queues across interfaces during a QoS commit. The read-back also recognizes the per-flow fq_codel entries created by actual traffic.

With 20 Mbps offered to each flow, native create measured 2.90 Mbps up and 7.73 Mbps down for the configured 3 and 8 Mbps. The 5 Mbps upload edit measured 4.83 Mbps with download at 7.73 Mbps. Both unmatched egress controls measured 20 Mbps. The gateway reconnected on the same acknowledged revision after a daemon restart. Network's System Log showed **Gateway Configuration Failed** when the VLAN 120 source edit was rejected. Router rates and controls held their previous values. The first withdrawal removed the live shapers and markers but left empty QoS interface nodes. The bridge held confirmation and VyOS rolled back on the timer. The targeted node deletion and exact empty-node regression passed on the automatic retry. The controller acknowledged removal, both interfaces returned to their default queues, and all four flows measured 20 Mbps. This gate covers the two pinned VLAN and WAN links on the single-WAN routed topology. Full suite passed 1,314 tests and five subtests with clean Ruff and diff checks.
